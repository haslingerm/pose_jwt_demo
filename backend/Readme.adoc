= JWT Demo -- Backend

Creates and stores JWT and refresh tokens for users.
A simple SQLite database is used to store data, so this project can be run as-is without any additional setup -- except for the signing key.

== Signing Key

The JWT signing key is a secret: whoever knows it can create valid tokens for any user and role.
So it must never be committed to the repository!
During development, it is stored in the https://learn.microsoft.com/en-us/aspnet/core/security/app-secrets[user secrets], in production it would be an environment variable or come from a key vault.

The key needs at least 32 bytes (256 bit), the application refuses to start otherwise:

[source,bash]
----
cd backend
dotnet user-secrets set "AuthSettings:TokenSigningKey" "$(openssl rand -base64 48)"
----

TIP: No `openssl`? Any random string with at least 32 characters works for the demo -- e.g. generated by your password manager.

== Trying it out

TIP: Take a look at link:./JwtDemo.http[`JwtDemo.http`] for a full run through all the endpoints (creating user, logging in, retrieving data, refreshing token).
Swagger UI is available at `/swagger` during development -- use the 'Authorize' button to enter an access token.

No production grade security is implemented in this demo!
Just sensible defaults -- except for the one endpoint that allows users to register as administrators, that one is just plain evil 😉 (and therefore only available during development).
Also, there is only minimal validation and not the cleanest architecture -- take those parts from other, dedicated examples!

Take it as a starting point for your own implementation.

== Notable C# Features

* C# 15 union types for service results, e.g. `union LoginResult(NewToken, InvalidCredentials)` -- the compiler checks that a `switch` expression handles all cases
* C# 14 extension blocks (`extension(IServiceCollection services) { ... }`) for setup and DTO mappings
* C# 14 `field` keyword (see `UnitOfWork`)
