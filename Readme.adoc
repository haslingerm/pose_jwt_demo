= JWT Demo

Typically, you want your applications to use OIDC providers to allow your users to 'login with GitHub' and similar services.
That is because security is _hard_ and logins/user data _has_ to be secure.

In an enterprise environment you would probably use something like a dedicated KeyCloak instance (as we do as well) or Microsoft Entra for AD integration etc.

However, for some small project you may still want to do local accounts.
And even if you use an external service you should still understand how things work and what is going on in the background.
Make sure you read the comments in the code, they give valuable insights and hints.

Built with .NET 11 (C# 15, ASP.NET Core minimal APIs) and Angular 22.

== Getting Started

. *Create the signing key secret* -- the backend refuses to start without it (see <<secrets>> for details):
+
[source,bash]
----
cd backend
dotnet user-secrets set "AuthSettings:TokenSigningKey" "$(openssl rand -base64 48)"
----
+
TIP: No `openssl`? Any random string with at least 32 characters works for the demo -- e.g. generated by your password manager.
. Start the backend: `dotnet run` in `backend` (the SQLite database is created automatically)
. Start the frontend: `npm ci` & `npm start` in `frontend`, then open http://localhost:4200
. Create users with the requests in link:backend/JwtDemo.http[`JwtDemo.http`] (registration is only available during development)

[[secrets]]
== Secrets: Signing Key & User Secrets

The JWT signing key is the most important secret of this application: whoever knows it can create valid tokens for _any_ user with _any_ role.
So it must never end up in the repository -- that is why `TokenSigningKey` is empty in `appsettings.json`, and the backend refuses to start if the key is missing or shorter than 32 bytes (256 bit, required by HMAC-SHA256).

=== During development: User Secrets

ASP.NET Core loads https://learn.microsoft.com/en-us/aspnet/core/security/app-secrets[user secrets] from a `secrets.json` file *outside* of the project directory, so it cannot be committed by accident.
The file belongs to the `UserSecretsId` in `JwtDemo.csproj` and is located at:

* Windows: `%APPDATA%\Microsoft\UserSecrets\ef6e2aa3-371f-47f5-b269-998f42d583e5\secrets.json`
* Linux/macOS: `~/.microsoft/usersecrets/ef6e2aa3-371f-47f5-b269-998f42d583e5/secrets.json`

You can create it with `dotnet user-secrets set ...` (see above), edit it with `dotnet user-secrets` or via your IDE ('Manage User Secrets' in Rider/Visual Studio).
After setting the key, it looks like this:

[source,json]
----
{
  "AuthSettings:TokenSigningKey": "<your random key>"
}
----

Its values override those of `appsettings.json` and `appsettings.Development.json`.
Every developer has their own file (and therefore their own key) -- tokens of one machine are not valid on another one.

IMPORTANT: User secrets are a development tool only: they are *not encrypted* and only loaded when the environment is `Development`.

=== When deployed: environment variables from a secret store

On a server, there is no user secrets file -- and it would not be read anyway, since the environment is not `Development`.
Instead, the key is usually provided as an *environment variable*, which ASP.NET Core reads automatically and which also overrides `appsettings.json`.
The `:` separator of nested settings becomes a double underscore:

[source,bash]
----
AuthSettings__TokenSigningKey=<your random key>
----

The value itself comes from a secret store and is injected by the deployment, never typed into a file in the repository or baked into a container image:

* CI/CD secrets (e.g. GitHub Actions/GitLab CI variables) which are passed to the container at deployment
* Docker Compose with an `.env` file that only exists on the server (and is listed in `.gitignore`), or Docker secrets
* Kubernetes secrets, mapped to environment variables
* Cloud key vaults (Azure Key Vault, AWS Secrets Manager, HashiCorp Vault, ...) -- some of them can also be added as a configuration provider directly

For example with Docker Compose -- the `.env` file next to `compose.yaml` contains `JWT_SIGNING_KEY=...` and is *not* committed:

[source,yaml]
----
services:
  backend:
    image: jwt-demo-backend
    environment:
      ASPNETCORE_ENVIRONMENT: Production
      AuthSettings__TokenSigningKey: ${JWT_SIGNING_KEY}
      AuthSettings__TokenIssuer: https://api.example.com
      AuthSettings__TokenAudience: https://app.example.com
      AppSettings__ClientOrigin: https://app.example.com
----

Things to keep in mind:

* Use a *different key per environment* (development, test, production) -- a token from a test system must not work in production.
* If you run *multiple instances* of the backend, they all need the same key, otherwise a token created by one instance is rejected by another.
* *Rotating the key* (e.g. after a leak) invalidates all access tokens immediately.
Our refresh tokens are random values checked against the database, not signed JWTs -- so they still work, and clients simply get new access tokens with the next refresh.
To log out everybody, delete the refresh tokens as well.
* The other settings (`TokenIssuer`, `TokenAudience`, `ClientOrigin`, connection string) are not secret, but also need production values -- `appsettings.json` only contains placeholders.

== Content

This demo project shows you:

* For the link:backend[backend]:
** Adding new users
*** With salted & hashed passwords (PBKDF2)
** Creating JWT tokens
*** With user claims, based on their roles
*** Short-lived access tokens and long-lived refresh tokens
*** Refresh token rotation: each refresh token can be used only once
*** Storing (hashes of) refresh tokens in a database
**** And removing them when expired or user logs out
** Validating JWT tokens (signature, algorithm, issuer, audience, lifetime)
** Minimal API endpoints (see link:backend/Readme.adoc[backend Readme])
*** Route groups per resource with `RequireAuthorization`, `AllowAnonymous` and `RequireRateLimiting`
*** Combining policies of a group and an endpoint (User role for all product endpoints, Admin role to change a price)
*** Typed results (`Results<Ok<T>, ValidationProblem, UnauthorizedHttpResult>`): the compiler checks the responses, and OpenAPI documents them automatically
*** Explicit request validation with FluentValidation, RFC 9457 problem details for validation errors and unhandled exceptions
*** Mapping an endpoint only in development (registration)
** Applying rate limiting to the auth endpoints
** Policies
*** Creating policies for different roles
*** Secure by default: all endpoints require authentication unless they opt out
** Providing a SignalR hub which checks for user auth state
*** And closes connections when the token expires
** Keeping the signing key secret (user secrets, environment variables)
* For the link:frontend[frontend]:
** Login & Logout
** Storing access and refresh tokens in local storage
** Automatically applying bearer token to requests
*** Only to our own API, and not for auth requests, which don't need them
** Role based auth guard for routes
** Automatically refreshing tokens
** Using token with SignalR connection
** Signal based login state, zoneless Angular and signal forms

== Security Measures

Besides the basics (hashed passwords, signed tokens) the following best practices are applied -- look for the comments in the code:

[cols="1,2"]
|===
|Measure |Why

|Signing key stored outside the repository, checked on startup
|Whoever has the key can create tokens for any user -- see <<secrets>>

|Constant time hash comparison, dummy hashing for unknown users
|Attackers cannot find out which usernames exist (or the stored hash) by measuring response times

|Same `401` for unknown user, wrong password and invalid refresh token
|Responses don't reveal which usernames exist

|Only refresh token _hashes_ are stored, tokens are rotated on every refresh
|A leaked database contains no usable tokens, a stolen refresh token becomes useless after the next refresh

|Accepted signing algorithm is pinned (`HS256`), minimum key length
|Prevents algorithm confusion attacks and weak keys

|Short access token lifetime, logout revokes the refresh token
|Access tokens cannot be revoked (without a blocklist), so they must expire quickly

|Rate limiting per client IP on all auth endpoints
|Slows down password guessing without locking out other users

|Fallback authorization policy
|Forgetting `RequireAuthorization` does not open up an endpoint

|Strict CORS policy, no credentials
|Only our frontend may call the API from a browser, no cookies involved

|SignalR connections are closed when the access token expires
|Otherwise a WebSocket connection would stay authenticated forever

|Explicit input validation (lengths, password min. length, ranges), strict JSON binding
|Rejects invalid and absurdly large inputs early

|Problem details without exception details
|Error responses don't leak internals, the `traceId` links them to the log entry

|TLS at the reverse proxy, forwarded headers only from trusted proxies
|Tokens are as good as passwords and must never be sent unencrypted; rate limiting needs the real client IP

|Frontend: token only sent to our API, single refresh at a time, tokens dropped on failed refresh
|No token leaks to third parties, no failed requests because of a reused refresh token
|===

CAUTION: As mentioned before, security is hard, and for this demo some shortcuts have been taken (see below). You may use it as a starting point, but don't deploy it as is!

Known shortcuts, which a real application would address:

* Anybody can register -- even as admin (the endpoint is at least only mapped during development)
* Tokens are stored in local storage, where an XSS vulnerability could steal them (see link:frontend/Readme.adoc[frontend Readme])
* No reuse detection for refresh tokens, no account lockout, no password breach check, no email verification
* No blocklist for access tokens (they stay valid until they expire, even after a logout)

TIP: If you use the `https` profile, you might have to trust the ASP.NET Development Certificate in your OS, which is then usually trusted by the browser as well -- otherwise you could get 'CORS' errors that are actually 'browser rejects certificate' errors.
The frontend uses the `http` profile (port 5106) by default, see `frontend/src/core/const.ts`.
