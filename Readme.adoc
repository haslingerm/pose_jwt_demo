= JWT Demo

Typically, you want your applications to use OIDC providers to allow your users to 'login with GitHub' and similar services.
That is because security is _hard_ and logins/user data _has_ to be secure.

In an enterprise environment you would probably use something like a dedicated KeyCloak instance (as we do as well) or Microsoft Entra for AD integration etc.

However, for some small project you may still want to do local accounts.
And even if you use an external service you should still understand how things work and what is going on in the background.
Make sure you read the comments in the code, they give valuable insights and hints.

Built with .NET 11 (C# 15) and Angular 22.

== Getting Started

. Set the JWT signing key (a secret, so it is stored in the user secrets and not in the repository) -- see link:backend/Readme.adoc[backend Readme]
. Start the backend: `dotnet run` in `backend` (the database is created automatically)
. Start the frontend: `npm ci` & `npm start` in `frontend`, then open http://localhost:4200
. Create users with the requests in link:backend/JwtDemo.http[`JwtDemo.http`] (registration is only available during development)

== Content

This demo project shows you:

* For the link:backend[backend]:
** Adding new users
*** With salted & hashed passwords (PBKDF2)
** Creating JWT tokens
*** With user claims, based on their roles
*** Short-lived access tokens and long-lived refresh tokens
*** Refresh token rotation: each refresh token can be used only once
*** Storing (hashes of) refresh tokens in a database
**** And removing them when expired or user logs out
** Validating JWT tokens (signature, algorithm, issuer, audience, lifetime)
** Applying rate limiting to the auth endpoints
** Policies
*** Creating policies for different roles
*** Securing endpoints with policies
*** Secure by default: all endpoints require authentication unless they opt out
** Providing a SignalR hub which checks for user auth state
*** And closes connections when the token expires
* For the link:frontend[frontend]:
** Login & Logout
** Storing access and refresh tokens in local storage
** Automatically applying bearer token to requests
*** Only to our own API, and not for auth requests, which don't need them
** Role based auth guard for routes
** Automatically refreshing tokens
** Using token with SignalR connection
** Signal based login state, zoneless Angular and signal forms

== Security Measures

Besides the basics (hashed passwords, signed tokens) the following best practices are applied -- look for the comments in the code:

[cols="1,2"]
|===
|Measure |Why

|Constant time hash comparison, dummy hashing for unknown users
|Attackers cannot find out which usernames exist (or the stored hash) by measuring response times

|Same `401` for unknown user, wrong password and invalid refresh token
|Responses don't reveal which usernames exist

|Only refresh token _hashes_ are stored, tokens are rotated on every refresh
|A leaked database contains no usable tokens, a stolen refresh token becomes useless after the next refresh

|Accepted signing algorithm is pinned (`HS256`), signing key length is checked on startup
|Prevents algorithm confusion attacks and weak keys

|Short access token lifetime, logout revokes the refresh token
|Access tokens cannot be revoked (without a blocklist), so they must expire quickly

|Rate limiting per client IP on all auth endpoints
|Slows down password guessing without locking out other users

|Fallback authorization policy
|Forgetting an `[Authorize]` attribute does not open up an endpoint

|Strict CORS policy, no credentials
|Only our frontend may call the API from a browser, no cookies involved

|SignalR connections are closed when the access token expires
|Otherwise a WebSocket connection would stay authenticated forever

|Input validation (lengths, password min. length, ranges)
|Rejects invalid and absurdly large inputs early

|HTTPS + HSTS outside of development
|Tokens are as good as passwords and must never be sent unencrypted

|Frontend: token only sent to our API, single refresh at a time, tokens dropped on failed refresh
|No token leaks to third parties, no failed requests because of a reused refresh token
|===

CAUTION: As mentioned before, security is hard, and for this demo some shortcuts have been taken (see below). You may use it as a starting point, but don't deploy it as is!

Known shortcuts, which a real application would address:

* Anybody can register -- even as admin (the endpoint is at least disabled outside of development)
* Tokens are stored in local storage, where an XSS vulnerability could steal them (see link:frontend/Readme.adoc[frontend Readme])
* No reuse detection for refresh tokens, no account lockout, no password breach check, no email verification
* No blocklist for access tokens (they stay valid until they expire, even after a logout)

TIP: If you use the `https` profile, you might have to trust the ASP.NET Development Certificate in your OS, which is then usually trusted by the browser as well -- otherwise you could get 'CORS' errors that are actually 'browser rejects certificate' errors.
The frontend uses the `http` profile (port 5106) by default, see `frontend/src/core/const.ts`.
